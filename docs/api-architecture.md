# Sigvitas HRMS — API Architecture

Status: Draft v0.1
Related: `architecture.md` §4–5, `authorization-model.md`, `security-architecture.md` §3, §5

> **2026-10-20, ADR-030:** the API is unchanged by the move to MongoDB. Behind it, rate-limit counters (§9) are in MongoDB, jobs (§10) run on the MongoDB lease scheduler, and download links are same-origin (`/api/v1/files/<token>`, 60 seconds).

## 1. Style

- JSON over HTTPS, resource-oriented REST. Actions that are not CRUD (approve, clock in, finalize) are explicit sub-resources: `POST /leave-requests/{id}/approve`, not `PATCH {status: "approved"}`. This keeps each state transition a separate, individually authorized and audited operation.
- One API for web and future mobile. No backend-for-frontend layer.
- Served under the same origin as the SPA: `https://<app-host>/api/v1/...`. No CORS.
- WebSockets (Phase 2+, at `/api/v1/ws`) only for push of notifications and chat events. Every piece of data delivered over WebSocket is also retrievable over REST; the socket carries "something changed" events and small payloads that passed the same authorization.

## 2. Versioning

- Path version: `/api/v1`. A new major version only for breaking changes; additive changes (new fields, new endpoints) stay in v1.
- The OpenAPI document is the contract. It is generated by FastAPI, committed to the repo (`api/openapi.json`) in CI, and the frontend types are generated from it. A CI check fails if the committed schema is out of date, making every contract change visible in review.
- OpenAPI docs UI is disabled in production.

## 3. Conventions

| Topic | Convention |
|---|---|
| Paths | Plural kebab-case nouns: `/employees`, `/leave-requests`, `/attendance-corrections`. |
| Self routes | `/me/...` for the actor's own data: `/me`, `/me/attendance/days`, `/me/leave/balances`. These never take an employee ID, removing a class of IDOR mistakes. |
| IDs | UUIDv7 strings. |
| Field names | `snake_case` in JSON (matches Python; generated TS types use the same names). |
| Dates / times | `date` as `YYYY-MM-DD`; timestamps as RFC 3339 UTC (`2026-09-30T04:15:00Z`). The client formats in the user's time zone. Work-date based resources are addressed by date. |
| Money | Format example: `{ "amount": "1000.00", "currency": "XXX" }` (ISO 4217 code; `XXX` is the ISO code for "no currency", used here as a placeholder). The amount is a string to avoid float rounding. |
| Enums | Lowercase strings, documented in OpenAPI. |
| Nullability | Absent optional fields are `null`, not omitted, in responses. Requests reject unknown fields (`422`). |
| Pagination | Keyset/cursor: `?limit=50&cursor=<opaque>`; response `{ "items": [...], "next_cursor": "..." \| null }`. `limit` max 100. No total counts on large lists (a separate count endpoint where the UI needs it). |
| Filtering | Explicit query parameters per endpoint (`?status=pending&from=2026-09-01&to=2026-09-30&department_id=...`). No generic query language. |
| Sorting | `?sort=work_date` / `?sort=-work_date` from an allow-list per endpoint. |
| Partial updates | `PATCH` with a per-audience model; every field optional; `If-Match: "<version>"` required. |
| Concurrency | Responses of versioned resources include `ETag: "<version>"`. Stale `If-Match` → `412 Precondition Failed`. |
| Idempotency | `Idempotency-Key` header required on clock events, correction/leave submissions, approvals and export requests. Replays within 24 h return the original response. Same key with a different body → `422`. |

## 4. Errors — RFC 9457 Problem Details

```json
{
  "type": "/problems/validation-error",
  "title": "Some fields need attention",
  "status": 422,
  "detail": null,
  "instance": "/api/v1/leave-requests",
  "request_id": "01J…",
  "errors": [
    { "field": "end_date", "code": "before_start_date", "message": "End date must be on or after the start date." }
  ]
}
```

`type` is a relative URI reference (`/problems/<name>`), so it is identical in every environment. Errors that have no defined type (for example `405`) use `about:blank` with the HTTP status phrase as the title.

Defined problem types (stable, used by the client for behaviour):

| Type | Status | Meaning |
|---|---|---|
| `unauthenticated` | 401 | No or expired session. Client attempts one refresh, then shows sign-in. |
| `invalid-credentials` | 401 | Any sign-in failure: unknown email, wrong password, wrong code, locked, disabled or not yet activated account. Identical for all, so it never reveals which. `code: login.challenge_expired` when the MFA step's token is used, expired or out of attempts (start again). |
| `forbidden` | 403 | Not permitted. |
| `step-up-required` | 403 | Needs MFA re-verification; includes `max_age_seconds`. |
| `mfa-enrolment-required` | 403 | Session is enrolment-only (recovery-code sign-in or admin MFA reset); only `/me/mfa/*` enrolment endpoints are allowed. |
| `not-found` | 404 | Missing or not visible to the actor. |
| `conflict` | 409 | State conflict (already approved, overlapping leave, invalid attendance sequence). Includes a machine code, e.g. `attendance.already_clocked_in`. |
| `precondition-failed` | 412 | Version mismatch. |
| `validation-error` | 422 | Field errors. |
| `rate-limited` | 429 | Includes `Retry-After`. |
| `internal-error` | 500 | Generic message and `request_id`. No stack traces. |
| `temporarily-unavailable` | 503 | A protective dependency (e.g. the rate-limit store for sign-in) is unavailable; includes `Retry-After`. |

Messages are written for users (see `ui-ux-guidelines.md` §9). Codes are for the client.

## 5. Authentication endpoints

| Method | Path | Notes |
|---|---|---|
MFA is mandatory for every account. No endpoint creates a full session from a password alone.

| Method | Path | Notes |
|---|---|---|
| POST | `/auth/login` | email + password. On success always returns `{ "mfa_token": ... }` (5 min, single-use, at most 5 wrong codes), never session cookies. A newer password step retires the account's earlier unused MFA token. |
| POST | `/auth/login/mfa` | `mfa_token` + TOTP → full session. `mfa_token` + recovery code → **enrolment-only session** (can call only the `/me/mfa/*` enrolment endpoints until a new factor is confirmed). |
| POST | `/auth/refresh` | Uses refresh cookie (web) or body token (mobile). Rotates. |
| POST | `/auth/logout` | Revokes current session. |
| POST | `/auth/step-up` | TOTP (passkey in Phase 2) → sets `step_up_at` and rotates session tokens. Password and recovery codes are not accepted. |
| GET | `/auth/invite/{token}` | Validate invite (returns only first name and whether valid). |
| POST | `/auth/invite/{token}/password` | Step 1: set password (policy-checked). Returns `enrolment_token` (30 min), required with the invite token by steps 2 and 3, so the emailed link alone cannot enrol an authenticator. |
| POST | `/auth/invite/{token}/mfa/totp/setup` · `/confirm` | Step 2: enrol and confirm TOTP. Confirming returns the recovery codes once, marks the account `active`, consumes the invite and creates a full session. |
| POST | `/auth/mfa-reenrolment/{token}` | After an admin MFA reset: password + emailed re-enrolment token → enrolment-only session. |
| POST | `/auth/password-reset` | Request; always `202` with the same body. 3 per hour per email, 10 per hour per IP (`429`; `503` when the rate-limit store is down). |
| POST | `/auth/password-reset/{token}` | Complete reset. Revokes sessions. Does not sign the user in; the next sign-in still requires MFA. |
| POST | `/me/password` | Change password (current + new, step-up). |
| GET | `/me/mfa/factors` | List own factors (labels, type, last used). |
| POST | `/me/mfa/totp/setup` · `/me/mfa/totp/confirm` | Add a factor (step-up, or allowed in an enrolment-only session). |
| DELETE | `/me/mfa/factors/{id}` | Remove a factor (step-up). Refused with `409 mfa.last_factor` if it is the last confirmed factor. |
| POST | `/me/mfa/recovery-codes` | Regenerate (step-up). |
| GET/DELETE | `/me/sessions`, `/me/sessions/{id}` | Own sessions. `DELETE /me/sessions` signs out every session except the current one and returns `{ "revoked": n }`. |
| GET/DELETE | `/me/devices`, `/me/devices/{id}` | Own trusted browsers (`current` marks this one). Forgetting one makes its next sign-in reported as new. |
| GET | `/me/login-history` | Own security events (login subset). |
| GET | `/me/elevation` | The elevation or break-glass that applies to the signed-in account now (`{ "elevation": null }` when none), for the elevation banner. |

Mobile clients send `X-Client-Type: mobile` on login to receive tokens in the body instead of cookies. This header is accepted only on `/auth/*` endpoints.

## 6. Authorization in the API layer

Each route declares its permission requirement:

```python
@router.post(
    "/leave-requests/{request_id}/approve",
    dependencies=[requires("leave.request.approve")],   # capability: any scope
)
async def approve_leave(request_id: UUID, body: LeaveDecision, ctx: Ctx = Depends(ctx)):
    return await leave_service.approve(ctx, request_id, body)  # resource check inside
```

- `requires(...)` checks the actor holds the permission at any scope (fast fail) and registers metadata for the route-coverage test.
- The service performs the resource-level check (scope, SoD, state, step-up) with the loaded resource.
- Public routes use `public_route()` explicitly; routes about the actor's own account use `account()` (any full session, or with `allow_enrolment=True` an enrolment-only one), and both are confined to allow-lists. The coverage test fails for a route with none of these, or more than one.
- Every route dependency returns the `Actor`, built once per request from PostgreSQL in a short transaction that closes before the route runs.

## 7. Response shaping

Response models are per audience, selected in the service by the actor's field-tier permissions for that subject:

```
GET /employees/{id}
  actor = self                → EmployeeSelfView      (internal + personal + masked sensitive)
  actor has profile.read.team → EmployeeTeamView      (internal only)
  actor has profile.read.all  → EmployeeHrView        (internal; + personal if personal.read.all)
  otherwise directory only    → EmployeeDirectoryView (directory fields)
```

Personal, sensitive and restricted data sit on separate sub-resources (`/employees/{id}/personal`, `/employees/{id}/identifiers`, `/employees/{id}/bank-accounts`, and in Phase 2 `/employees/{id}/compensation`) so each has its own permission, step-up and audit behaviour, and caching or logging of the main resource can never include them.

## 9. Rate limits

Two layers: coarse per-IP limits at the proxy, and application limits whose counters live in Redis (sliding window, ephemeral). Account lockout is separate and lives in PostgreSQL. Behaviour when Redis is unavailable is defined per row in `architecture.md` §3.1: auth, download and export limits fail closed (`503`), general API limits fail open with an alert.

| Scope | Limit |
|---|---|

| Same, per target account | see lockout policy (`security-architecture.md` §3.4) |

## 10. Background jobs contract

Jobs are defined in the owning module and enqueued inside the business transaction:

| Job | Trigger | Idempotent by |
|---|---|---|
| `attendance.recompute_day(employee_id, work_date)` | event, correction decision, leave decision, shift/policy/holiday change | overwrite of projection |
| `attendance.recompute_range(scope, from_date)` | new shift or attendance policy version | fan-out to `recompute_day` |
| `attendance.materialize_days(date)` | nightly | unique `(employee_id, work_date)` |
| `attendance.flag_incomplete(date)` | periodic; uses each policy's `incomplete_after_minutes` | projection recompute |
| `leave.accrue(period)` | schedule derived from each policy's accrual frequency | unique accrual constraint |
| `leave.year_end(policy, leave_year)` | each policy's own leave-year start | unique carry-forward/lapse constraint |
| `access.expire_grants()` | every minute | status transition; permissions already stop applying at `ends_at` because they are resolved per request |
| `audit.ensure_partitions()` | hourly; keeps the current month and three ahead for both audit streams | creates only missing partitions (advisory lock) |
| `audit.seal()` | every minute, both streams, single instance (job lock and an advisory lock per stream) | position sequence; a row is sealed once (unique record per partition) |
| `audit.checkpoint()` | hourly at :07: partition-final once a month ended more than 1 h ago, daily once per UTC day per changed partition; anchors new checkpoints and retries missing ones | unique final per partition; gap-free checkpoint numbers (trigger) |
| `audit.verify_recent()` / `audit.verify_full()` | daily at 02:30 UTC / monthly on the 1st at 03:40 UTC | read-only; a mismatch records `audit.chain_mismatch` and alerts super admins and auditors once per stream, scope and day |
| `audit.retention()` | daily at 04:20 UTC, as `hrms_audit_retention`; only when a period is configured, only eligible partitions | verified, then tombstone before drop; a written tombstone is reused |
| `notify.dispatch_email()` | every minute; claims due outbox rows (`SKIP LOCKED`, lease) | idempotency key per event; outbox status |
| `docs.scan_version(version_id)` | upload | `scan_status` |
| `exports.generate(export_id)` | export request | job status |
| `identity.apply_scheduled_deactivations()` | every 5 min | user status |
| `retention.*` (non-audit data) | daily | date-based |

Built so far beyond the audit and email jobs (2026-10-15): `documents.scan` (every minute, up to 20 pending versions, at most 5 attempts before `failed`; not registered, so files stay pending, when `CLAMAV_HOST` or `FILES_BUCKET` is not set; deployed workers refuse to start without `CLAMAV_HOST` unless uploads are turned off), `reports.exports` (every minute, up to 5 queued exports, at most 3 attempts; also deletes files past their 24 hours and marks them `expired`) and `leave.accrue` (daily at 00:15 UTC: due periodic accruals and carried-day expiry). Attendance days are derived when read, so the `attendance.*` recompute jobs above are not needed yet.

Failed jobs retry with backoff (max 5); permanent failures raise an operational alert and are visible to system admins.

## 11. Real-time (Phase 2+)

- WebSocket authenticated by the session cookie during the handshake; Origin checked.
- The server subscribes a connection only to channels derived from the user's identity (`user:{id}`) and, for chat, conversation memberships re-checked on every subscribe and on membership change.
- Events contain IDs and a type; the client refetches details over REST, which re-applies authorization. Fan-out across API replicas is decided in Phase 2: PostgreSQL `LISTEN/NOTIFY` first, Redis pub/sub only if measured load requires it (`architecture.md` §3.1). Either way the channel carries notifications only, never authoritative data.
- Server-Sent Events are an acceptable simpler alternative if chat is never built; the decision is deferred to Phase 2.

## 12. Client integration rules

- The SPA uses a single fetch wrapper: adds `X-Requested-With: sv-web`, handles `401` by one refresh attempt, handles `step-up-required` by opening the step-up dialog and retrying, maps problem details to form errors.
- Generated types from OpenAPI; Zod schemas for form validation mirror server rules for fast feedback, but the server is authoritative.
- TanStack Query keys follow `[module, resource, params]`; mutations invalidate by module prefix.
